# AI Context: Dictionary Backend

## Что это за проект

Это backend для **offline-first словаря с нейросетями**.

Основной клиент — **мобильное приложение на Expo**.  
В будущем приложение также должно работать **в вебе**, используя тот же backend.

---

# Цель проекта

Основная задача — помогать людям изучать слова иностранного языка, **генерируя контекст для них**, чтобы:

- было интереснее их учить
- было легче запоминать
- пользователь сразу понимал, **где и как использовать слова**

Пользователь добавляет слова в виде **карточек**, после чего приложение может генерировать обучающий контент на основе этих карточек.

---

# Архитектура

Приложение использует **offline-first подход**.

### Клиент

Основные данные хранятся **локально на устройстве пользователя** при помощи **SQLite**.

Локально хранятся:

- карточки
- тренировочные пресеты
- результаты тренировок
- истории
- другие пользовательские данные

Клиент должен **работать без сети**, кроме AI функционала.

Основная платформа — **мобильные устройства**, но приложение также должно работать **в вебе**.

---

### Backend

Backend выполняет следующие задачи:

- синхронизация данных между клиентом и сервером
- хранение пользовательских данных
- работа с нейросетями
- авторизация и регистрация пользователей

Backend **не является единственным источником истины**, потому что клиент должен продолжать работать **в offline режиме**.

## Архитектурный стиль backend

Проект должен оставаться **небольшим modular monolith на NestJS**.

Основной принцип структуры:

- backend организован **по бизнес-модулям**, а не по глобальным папкам `controllers`, `services`, `utils`
- каждый модуль должен быть **feature-first**
- внутри модуля используется простое разделение на слои:
  - `presentation` — HTTP-слой
  - `application` — use case / сценарии
  - `infrastructure` — внешние интеграции
- `domain` добавляется **только если действительно появилась отдельная бизнес-логика**, а не заранее

Нужный уровень сложности:

- не использовать тяжёлую clean architecture или DDD ради формы
- не дробить проект на микросервисы
- не вводить абстракции "на будущее", если они ещё не нужны

## Целевая структура папок

Пример целевой структуры:

```text
src/
  main.ts
  app.module.ts

  common/
    dto/
    filters/
    guards/
    interceptors/
    pipes/

  config/
    ...

  modules/
    ai/
      ai.module.ts
      presentation/
      application/
      infrastructure/

    auth/
      auth.module.ts
      presentation/
      application/
      infrastructure/

    cards/
      cards.module.ts
      presentation/
      application/
      infrastructure/

    sync/
      sync.module.ts
      presentation/
      application/
      infrastructure/
```

Если модуль пока маленький, допускается не создавать все подпапки сразу, но направление структуры должно оставаться таким же.

## Правила слоёв

### `presentation`

Содержит:

- NestJS controllers
- request/response DTO
- HTTP-specific mapping

Не должен содержать:

- прямые вызовы AI/API/БД
- тяжёлую бизнес-логику
- парсинг ответов провайдеров

### `application`

Содержит:

- use cases
- orchestration-логику
- координацию между infrastructure и domain

Не должен содержать:

- детали HTTP
- сырой код работы с `axios`, SDK провайдеров, SQL и т.д.

### `infrastructure`

Содержит:

- AI providers / clients
- repository implementations
- config adapters
- prompt builders, если они тесно связаны с интеграцией

Не должен содержать:

- контроллеры
- публичные HTTP DTO

### `domain`

Используется только когда появляются:

- отдельные бизнес-правила
- value objects
- внутренние типы, не равные HTTP DTO
- инварианты предметной области

Если логики ещё мало, можно временно обойтись без `domain`.

## Правила зависимостей

Допустимое направление зависимостей:

- `presentation -> application`
- `application -> domain`
- `application -> infrastructure`

Нельзя:

- импортировать `presentation` внутрь `infrastructure`
- делать глобальные общие `utils`, если они относятся только к одной фиче
- смешивать DTO HTTP-слоя с внутренними моделями без необходимости

Практическое правило:

- если код отвечает на вопрос "как принять HTTP-запрос?" — это `presentation`
- если код отвечает на вопрос "что должен сделать backend?" — это `application`
- если код отвечает на вопрос "как сходить во внешний мир?" — это `infrastructure`

## Архитектурные правила генерации

При дальнейшей генерации кода агенты должны придерживаться следующих правил:

- новые фичи добавлять в `src/modules/<feature>`
- не создавать глобальные папки вида `src/services`, `src/controllers`, `src/repositories`
- не складывать всю логику модуля в один большой `*.service.ts`, если сервис начинает совмещать несколько сценариев
- DTO хранить в `presentation/dto`
- внешние AI-провайдеры хранить в `infrastructure/providers`
- промпты и парсеры AI-ответов хранить рядом с AI-модулем, а не в глобальных shared-папках
- общие вещи выносить в `src/common` только если они реально переиспользуются несколькими модулями
- конфигурацию и env-логику держать централизованно, а не читать `process.env` хаотично по всему проекту
- для новых модулей сначала выбирать простую структуру, а не максимальную абстракцию

## Специфика offline-first

Так как проект offline-first, backend не должен проектироваться как единственный источник истины.

Это означает:

- sync-логика является core-частью архитектуры, а не второстепенным CRUD
- нужно избегать решений, требующих постоянного online-соединения
- контракты синхронизации должны быть простыми и устойчивыми к конфликтам
- удаление данных в будущем лучше проектировать с учётом `deletedAt` / tombstones, а не только физического удаления
- API не должен предполагать, что клиент всегда имеет актуальное серверное состояние

## Что считается плохой архитектурой для этого проекта

Нежелательные направления:

- глобальная структура `controllers/services/repositories` на весь проект
- один огромный `AppService`, в который со временем складывается вся логика
- преждевременная сложная абстракция без реального кейса
- сильная связность AI-логики, sync-логики и CRUD в одном модуле
- утечка server-only логики или AI ключей в клиентские контракты
- проектирование backend так, как будто offline-first требований не существует

# Работа с нейросетями

Нейросети используются для генерации обучающего контента на основе карточек пользователя.

Основные функции:

### 1. Генерация тренировочных упражнений

Создание упражнений на основе карточек пользователя.

### 2. Генерация интерактивных историй

Создание историй, в которых используются слова пользователя.

Истории могут содержать:

- контекст использования слов
- несколько вариантов развития событий
- выбор действий пользователем

---

# Безопасность AI

API ключи нейросетей **никогда не должны находиться на клиенте**.

Все запросы к нейросетям выполняются **через backend**.

Архитектура запросов:
client → backend → AI provider

Используемые AI провайдеры:

- OpenRouter

Пользователи **не используют собственные AI ключи**.

Backend использует **серверные ключи** и может управлять:

- лимитами
- usage
- кэшированием ответов

# What AI agents should keep in mind

When modifying this project:

- preserve offline-first assumptions
- never expose AI API keys to clients
- keep architecture simple
- prefer modular NestJS structure
- avoid unnecessary abstractions
- keep code organized by `src/modules/<feature>`
- keep controllers and DTO in `presentation`
- keep orchestration logic in `application`
- keep provider and integration code in `infrastructure`
- do not reintroduce project-wide folders like `src/services` or `src/controllers`
